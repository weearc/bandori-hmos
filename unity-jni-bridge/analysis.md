# Original libmain JNI entry, ARM64

Evidence: extracted unmodified lib/arm64-v8a/libmain.so from the local APK; llvm-objdump -d --disassemble-symbols=JNI_OnLoad and llvm-readelf -x .rodata -r.

JNI_OnLoad at 0x4a70 calls JavaVM vtable slot 4 (offset 32, AttachCurrentThread) with a pointer to a local JNIEnv* and null attach args. It does not check the return before dereferencing the environment. JNIEnv slot 6 (offset 48, FindClass) resolves com/unity3d/player/NativeLoader. Slot 215 (offset 1720, RegisterNatives) registers two entries from relocated table 0xd138: load (Ljava/lang/String;)Z -> 0x4b00 and unload ()Z -> 0x4bdc. Negative registration result invokes slot 18 FatalError; success returns JNI_VERSION_1_6 (0x10006). This entry itself does not load Unity.

When Java later invokes load, it uses slots 168/169/170 GetStringUTFLength/GetStringUTFChars/ReleaseStringUTFChars, and calls helper 0x4cd8 for libunity.so then libil2cpp.so. Helper uses slot 219 GetJavaVM, dlopen(path/name then name), dlsym JNI_OnLoad, and invokes it with the real VM; a return >= 0x10007 is fatal. unload uses GetJavaVM, resolves JNI_OnUnload and calls it, then dlclose. The registered pointers and class must remain valid throughout registration/use; class resolution, thread attachment, pending exceptions, native binding, and VM lifecycle must be genuine. FatalError is process terminating per JNI semantics, so this entry cannot safely be probed with incomplete VM support.

No original JNI_OnLoad or game code was called. Actual libunity/libil2cpp JNI requirements remain unknown until independently inspected. The current DVM integration has no production JNI table or complete native registration/dispatch and is insufficient to invoke this entry safely. A bridge must implement real thread attachment, reference lifetimes, DVM class and native-method resolution with descriptor validation, and error behavior before invocation; a partial fake table would crash or misrepresent success.
