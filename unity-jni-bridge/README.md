# JNI registration bridge subset

> Audit note (2026-11-02): The text below contains historical module states and build instructions. Read the [current audit requirements](../README.md) and [handoff](../handoff.md) before using it; old pending/current claims do not supersede later device reports. Original game JNI_OnLoad and Unity execution remain unverified.

Build: `clang++ --target=aarch64-linux-ohos --sysroot=<native-sdk>/sysroot -std=c++17 -fPIC -shared bridge.cpp -o libjni_bridge.so -Wl,--no-undefined` (SDK clang++ succeeded).

The provider must resolve actual DVM classes and check exact DEX native declarations. It owns stable class identities for the VM lifetime. Calls into the provider must not reenter registration (the registry lock is held). Registered function pointers remain owned by their loaded library; prevent unloading while registered or callable. `jb_lookup_native` returns the actual registered pointer, not a simulated result.

Each attached thread must detach before termination. The owner must externally synchronize destruction against attach, lookups and callbacks; destruction fails while threads remain attached. Class handles are stable until VM destruction, not a complete JNI local/global reference implementation. Error text is a bridge-local pending state, not a DVM throwable; it must be translated into the real DVM exception model before integration. Vtable entries not implemented are null and must never be called. This is an incomplete subset, not permission to invoke game JNI_OnLoad: native loading, JNI strings, exception objects, full reference semantics, provider integration, and validation remain outstanding. No original game entry point has been called.

`dvm_provider.c` binds to the generated DVM private structures and the real `dvm_find_class` / `dvm_find_method` symbols. The object compiles for ARM64, with those symbols intentionally unresolved until linked to the matching DVM build. The ABI depends on the exact generated internal headers. Call under the DVM's required lock and keep DVM and DEX memory alive until the bridge and all users are gone. The adapter rejects external/synthesized classes and inherited or non-DEX/non-native methods.

`bridge_test.cpp` exports `jb_self_test(struct dvm *)`: pass a loaded DVM to additionally check both NativeLoader declarations. It tests the bridge using a separate synthetic provider, not game execution. It is compiled but has not been run. Compile with OpenJDK's `jni.h` and this directory's `jni-platform/jni_md.h`; the latter supplies ARM64 scalar types and calling convention, avoiding the Windows JDK's incompatible platform definitions. Static assertions check the table offsets used by the test. The method metadata inventory independently lists the two signatures in classes2.dex, but a live DVM check is still pending.

`libjnibatch.so` exports `const char *jni_batch_run(const char *dexdir)`. The caller must serialize it with every shared sdktrace arena user. It creates a DVM with zero hooks, loads exactly three DEX files, runs the self-test, and destroys the DVM. The v8/v9 DVM owns arena begin/end internally; the wrapper must not begin another arena. The returned thread-local report stays valid until the next call on that thread. Self-test code 1–10 identifies fixture bridge failures, 11–13 identify real DVM NativeLoader metadata failures. No original native or DEX method is invoked. Its dependency `libsdktrace.so` and the headers used for `dvm_provider.o` must match in private `dvm_class` and `dvm_method` layout; this build used the current sdk-runtime-spike/generated headers and v8 sdktrace. It also needs `libc++_shared.so` at runtime. ARM64 linking used --no-undefined and readelf confirms DT_NEEDED libsdktrace.so; runtime validation is pending.
