# Unity theme and pre-mount path

Guest profile defaults to Android API 28. Original APK SHA-256 `2ff2baf1b8fe78692b67507f88d3849422b672a0a929b374a878e1087d1519ec`: manifest application theme `0x7f0e0115` UnityThemeSelector; MainActivity has no theme override. The diagnostic standalone UnityPlayerActivity is not declared in the original manifest; using the application theme for that diagnostic is a runtime choice. APK resource table: selector -> BaseUnityTheme `0x7f0e00a1`, API 28 variant parent `0x01030242`, no `windowIsTranslucent` declaration. The v31 variant parent is `0x010300f1` and is not selected for API 28.

[AOSP Android 9 public.xml](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-9.0.0_r1/core/res/res/values/public.xml) maps 0x01030242 to Theme.Material.Light.NoActionBar.Fullscreen. Its implicit parent chain in [themes_material.xml](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-9.0.0_r1/core/res/res/values/themes_material.xml) goes through Theme.Material.Light.NoActionBar -> Theme.Material.Light, whose explicit parent is Theme.Light; [themes.xml](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-9.0.0_r1/core/res/res/values/themes.xml) continues Theme.Light -> Theme. No style in that chain declares `windowIsTranslucent` (0x01010058). Hence it is absent in this AOSP resource chain, and original i0.a() uses its actual `getBoolean(0,false)` default. This is not evidence for vendor overrides or runtime theme changes. Android 9 public.xml identifies the unused v31 parent as Theme.Holo.Light.NoActionBar.Fullscreen; [themes_holo.xml](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-9.0.0_r1/core/res/res/values/themes_holo.xml) likewise leads to Theme.Light with no declaration.

After initJni, cached original UnityPlayer constructor performs W0 state update; constructs i0 (SurfaceView holder setFormat/addCallback, resource identifier, view ID, focus/content description/layout); addView and bringChildToFront; Activity.getWindow and hideStatusBar; phone and clipboard system services; constructs Camera2Wrapper and HFPStatus; starts main thread; and invokes D.a for back dispatcher. These branches and platform operations must run before constructor return. Cached UnityPlayerActivity.onCreate then stores the player field and calls setContentView; requestFocus follows it. There is no additional framework call between the completed constructor and setContentView besides the field store. Current implementation/host readiness for each constructor operation is not established by static source; observe actual execution and do not fabricate services, mount, or callbacks.
