## Source review
- Root follow-up: `jni_bridge.c` bridge_pin_cb/bridge_unpin_cb (around1197) do call dvm_pin/dvm_unpin for local/global object references; the comment explicitly excludes weak/class tokens. Therefore an audit must not assume all JNI refs are unrooted. The pin callback returns true after the void dvm_pin call; verify the particular reference was live at publication before treating pinning as a lifetime guarantee. No capture yet links this boundary to a historical fault.
- `native-jni-next/jni_bridge.c`: inspect JNI ref creation/deletion and method lookup/cache paths; local refs are scoped while global refs must remain rooted until deletion. The current file has lookup/ref helpers but this review found no capture-to-cache pointer chain proving the fault.
- `sdk-init-next/dvm.c`: heap/object slots and method caches exist; the source has a global interpreter lock and comments that methods/classes are freed only during teardown (`dvm.c:5685-5689`). This does not establish object pinning or rule out stale guest handles across native calls. A NULL class/object-data read warrants tracing handle allocation, slot recycle, and root lifetime against the 72gd access.
- `native-elf-loader-next/elf_loader.c`: loader registry is protected by `g_mu` (`:204`); Android ABI symbol routing begins around `:651`. This is evidence of some synchronization, not proof every returned symbol/function lifetime is protected.
- `native-elf-loader-next/android_dlfcn.c`: adapter handle table uses once-initialized recursive mutex (`:20,40-45`); handle lookup/open/close and portions of dlsym are locked (`:66-74,117-145`). Custom symbol resolution deliberately unlocks around some operations (`:130-139`), so inspect lifetime/close interleavings if loader evidence points there. No global lazy function cache was tied to these captures in this audit.

### Signal handler review
`native-elf-loader-next/native_fault_probe.c:167-197` adds `syscall(SYS_prctl, PR_GET_NAME, ...)` in the handler. This raw syscall is appropriate for avoiding `pthread_getname_np`; supported Linux/HarmonyOS syscall behavior should still be checked at compile/runtime, and failure should simply omit name. The handler also uses raw gettid, `write`, and previously existing safe-read routines. `safe_read_range` uses `process_vm_readv` at lines 82-100; confirm syscall availability/behavior on target, and treat `read=fail` as lack of evidence. Signal forwarding/restoring handlers after logging is pre-existing complexity; do not interpret logger behavior as transparent if prior handler exists.

Normal-context map capture at lines 236-239 uses fopen/fgets/fprintf before installing handler, so it does not add those non-async-safe calls to signal context. It records `/proc/self/maps` for the process at probe initialization; mappings can later change, and the file is capped at 4096 lines. This is useful for resolving the captured PC only if the map snapshot corresponds to that PID and relevant mapping remained loaded. N10's existing run09 capture predates these additions and contains only probe/libc `dladdr` entries; it does NOT contain map snapshot or thread name. In that record, PC is in neither reported probe nor libc mapping, so exact module attribution is unavailable from this file alone. New mappings would address module coverage at initialization but not prove a later unload/reload mapping state; report the gap.

### Object dump limitation
The generic x19 dump at lines 133-166 is raw memory around a callee-saved register. Even if readable and structurally plausible, arbitrary x19 is not evidence of a DVM object, class pointer, or UAF. The prior comment's PlayerPrefs/log-formatter interpretation is conditional and cannot generalize to every fault site. In run09, x19 points to readable bytes, but `object_data=0 read=fail`; this alone proves neither object identity nor NULL class/UAF. Label it `x19_window`/`x19_plus_0x10` or clearly qualify it as an untyped register window. For a DVM claim, require fault PC/callsite attribution plus a runtime-specific object-layout check (class/slot/generation/heap membership) from a safe diagnostic path.
