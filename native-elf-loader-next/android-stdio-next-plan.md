# Android stdio compatibility plan (read-only evidence)

## Findings

The original `rea-analysis-20261104/il2cpp-s.txt` lists strong undefined imports from `LIBC`: object `__sF`; functions `fprintf`, `vfprintf`, `fclose`, `fflush`, `fopen`, `fread`, `fseek`, `fseeko`, `ftello`, and `fwrite`. The complete stdio surface evidenced by this symbol table is exactly that set (not an inference from source-level use). `il2cpp-r.txt` has one dynamic relocation to `__sF`: `.rela.dyn` offset `0x644ba28`, type `R_AARCH64_GLOB_DAT`, symbol index `0x25`, addend 0. This establishes address-taking/storage via a GOT relocation, but does not prove all uses are passed as opaque arguments: indirect loads, pointer arithmetic, or field access require disassembly/dataflow inspection.

## ABI boundary

Android 14 bionic (AArch64 LP64) `FILE` is `struct __sFILE` and is 152 bytes with 8-byte alignment in the pinned header below. This is a private implementation layout, not a portable ABI. OH `FILE` comes from the installed OpenHarmony sysroot and is an independent libc object/layout; its pointer must only be consumed by OH stdio. Do not allocate an Android-shaped `FILE`, reinterpret an OH `FILE`, or concatenate three OH `FILE` objects to fake bionic's `__sF[3]` array. The two libcs own separate stream state and may have incompatible buffering, locks, descriptors, and lifetime rules.

On Android, `__sF` is the legacy exported array of three `FILE` objects; its element addresses represent stdin, stdout, stderr (indices 0, 1, 2). `stdin`, `stdout`, `stderr` are macros/accessors based on those stream objects in the pinned bionic headers; `__stdin`, `__stdout`, `__stderr` are not imported by this IL2CPP image and must not be assumed to be aliases or present on OH. The original binary's imported symbol is specifically `__sF`, not the three named pointers.

## Minimal complete bridge proposal

Use a private token domain for the three Android standard streams. Export a synthetic `__sF` address backed by three opaque, correctly aligned token slots, never as `FILE` storage. Force resolution of `__sF` and every listed stdio function to this bridge **before** system-library scope and `RTLD_DEFAULT`; otherwise a system symbol can bind to a foreign libc object and evade the existing placeholder guard. For a stream argument, recognize only the three exact token addresses and translate to the corresponding genuine OH standard `FILE *` obtained from the OH libc's supported `stdin`/`stdout`/`stderr` interface. For a pointer returned by OH `fopen`, retain/recognize it as an OH-owned file pointer and pass it only to OH stdio wrappers. Reject unknown pointers rather than forwarding across libc boundaries.

Implement wrappers for all imports above, including both formatted output entry points (`fprintf` and `vfprintf`), close/flush, open, block read/write, both seek forms, and tell. `fclose` on a standard token should follow the selected Android-compatible behavior (normally reject/return EOF; never close OH process standard streams); `fflush(NULL)` must preserve libc semantics by flushing all OH streams available to the bridge. Ensure errno and return-value semantics are translated, `fopen` pointer ownership is tracked, and closed pointers are invalidated. Add concurrency-safe state if wrappers maintain ownership metadata. Keep constructor-time strict rejection until every imported call path is routed to this implementation.

## Targeted reference check (static, candidate list)

The LLVM candidate list is `batch-validation/unity-bootstrap-20261109/il2cpp-sf-got-references.json`; it enumerates 74 ADRP/LDR candidates (some duplicate addresses) for GOT slot `0x644ba28`. The list is explicitly candidate-only because its 8-instruction heuristic can misassociate unrelated LDRs. Targeted `llvm-objdump -d --section=.text` windows show the predominant use is `ADRP x8,0x644b000; LDR x8,[x8,#2600]; ADD ...,x8,#304`, which is byte offset 304 = 2 * 152, the Android stderr element address, then passes that address as FILE* to `fprintf` and often `fflush`.

Confirmed call patterns include `0x27a45ac` / `0x27a5880` / `0x27b41a8` -> `fprintf(stderr,...)` then `exit`; `0x289f5dc` -> `vfprintf(stderr,...)` then `fputc(...,stderr)`; `0x28b6c60` and `0x28b6d1c` -> `fprintf(stderr,...)`, `fflush(stderr)`, `abort`; `0x28ba624` -> `fwrite(...,stderr)`. Many candidate sites in `0x28b8d08`–`0x28b8e38`, `0x28b93000`–`0x28b946xx`, `0x28b9c98`–`0x28b9dd0`, and `0x28ba4b0` / `0x28baa58` similarly form stderr pointers and branch to shared `fprintf`/`fflush`/`abort` blocks. These are direct evidence that the stream pointer is passed to libc stdio entry points, not evidence of a portable/opaque FILE contract.

One candidate, `0x28ba194`, is materially different: it loads `__sF` to x11, adds 304 into x21, then nearby code has `mul x10,...,#56; ldr w10,[x8,x10]` for unrelated runtime table work. The short window does not establish any dereference of x21, but it also does not close the full function's dataflow. The duplicate and multi-entry candidates around the shared error-reporting blocks also mean the supplied list is not a complete semantic classification. No reviewed window demonstrates a FILE-field load/store; this is a bounded observation, not proof that none exist. Before treating tokens as sufficient, trace every unique ref through its containing function, inspect all uses of the derived +304 pointer and search globally for other __sF-derived constant offsets/loads, especially +0/+152 and fields. Until that is complete, direct FILE field access remains an open risk and the safe wrapper plan remains conditional.

Evidence excerpts and unknowns are cached in `native-elf-loader-next/android-stdio-evidence.txt`. Runtime `sf_placeholder=not-used` establishes only that the shim was not selected in that run; it does not identify which system object supplied `__sF`. The GOT's actual binding source still requires the loader's new binding diagnostic / device confirmation.
